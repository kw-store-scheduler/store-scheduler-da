# Part 1. 최적화 엔진

## 1. 기술 스택 및 기본 구조

### 사용 기술

| 항목 | 내용 |
|------|------|
| 언어 | Python 3.x |
| 최적화 라이브러리 | Google OR-Tools CP-SAT (`ortools.sat.python.cp_model`) |
| 백엔드 연동 | Spring Boot (REST API 호출 → `solve_schedule(config)` 반환) |

### CP-SAT 선택 이유

CP-SAT(Constraint Programming + Boolean SATisfiability)는 스케줄링처럼 **이진 결정변수**(근무함/안 함)와 **복합 제약**이 공존하는 문제에 특화된 솔버다. 선형 계획법(LP)보다 표현력이 높고, 정수 계획법(MIP) 대비 실전 스케줄 문제에서 빠른 수렴을 보인다.

### 결정 변수

```
work[e, d, s] ∈ {0, 1}
  e : 직원 인덱스
  d : 날짜 인덱스 (0-based)
  s : 교대 인덱스
```

직원 e가 날짜 d에 교대 s로 근무하면 1, 아니면 0.

### 하드 제약 (반드시 준수)

| 번호 | 내용 | 구현 방식 |
|------|------|-----------|
| 하드 1 | 가용 요일 외 근무 불가 | `model.Add(work[e,d,s] == 0)` |
| 하드 1-1 | 요일별 가용 시간 외 교대 근무 불가 (3차 추가) | `unavailable_slots`의 (day, shift)마다 `model.Add(work[e,d,s] == 0)` |
| 하드 2 | 하루 최대 1교대 (이중 근무 금지) | `model.AddAtMostOne(...)` |
| 하드 3 | 주간/월간 최대 근무시간 초과 금지 | `model.Add(weekly_hours <= max_hours)` |
| 하드 4 | 연속 5일 이상 근무 금지 | 5일 슬라이딩 윈도우 합산 ≤ 4 |

## 2. 문제 1 — 인원 부족 시 스케줄 자체가 생성되지 않던 문제

### 발생 상황

교수님 피드백: "월요일에 3명이 필요한데 가용 인원이 2명뿐이면 어떻게 되나요?"

초기 코드는 교대별 최소 인원을 **하드 제약**으로 처리하고 있었다.

```python
# 구 코드 — [하드 5]
for d in range(D):
    for s in range(S):
        model.Add(sum(work[e, d, s] for e in range(E)) >= min_s[s])
```

가용 인원이 최소 인원보다 적으면 이 제약을 절대 만족시킬 수 없으므로 OR-Tools는 즉시 **INFEASIBLE**을 반환하고 스케줄을 전혀 생성하지 않았다.

### 해결 방법: 하드 → 소프트 제약 전환

`[하드 5]`를 완전히 제거하고, 대신 **소프트 제약**으로 대체했다. 위반 시 매우 높은 패널티를 부과해 가용 인원이 있으면 반드시 채우도록 유도하되, 인원 자체가 부족한 경우에도 스케줄은 생성하고 부족 현황을 보고한다.

```python
# 신 코드 — [소프트 0]
MIN_STAFF_W = 50_000_000  # 1명 부족 = 5천만 패널티

for d in range(D):
    for s in range(S):
        actual = sum(work[e, d, s] for e in range(E))
        for k in range(1, min_s[s] + 1):
            v = model.NewBoolVar(f"ms_{d}_{s}_{k}")
            model.Add(actual <= k - 1).OnlyEnforceIf(v)   # v=1 ↔ actual < k
            model.Add(actual >= k).OnlyEnforceIf(v.Not())
            min_shortage_vars.append(v)
```

### 결과

| 상황 | 구 버전 | 신 버전 |
|------|---------|---------|
| 인원 충분 | OPTIMAL + 스케줄 | OPTIMAL + 스케줄 |
| 인원 부족 | **INFEASIBLE + 스케줄 없음** | **OPTIMAL + 스케줄 + shortage_report** |

## 3. 문제 2 — 복수 최적해 감지 및 처리

### 발생 상황

교수님 피드백: "최적해가 여러 개인 경우 어떻게 처리할 것인가?"

CP-SAT는 최적해를 **하나만** 반환한다. 동일한 목적함수 값을 가진 다른 배정 방식이 존재하는지 알 수 없었다.

### 해결 방법: No-Good Cut 기법

첫 번째 최적해를 찾은 뒤, 그 해를 **배제하는 절(No-Good Cut)**을 모델에 추가하고 재풀기를 반복한다. 재풀기 결과의 목적함수 값이 첫 번째와 동일하면 또 다른 최적해가 존재하는 것이다.

```python
def _add_no_good_cut(model, work, solver, E, D, S):
    literals = []
    for e in range(E):
        for d in range(D):
            for s in range(S):
                if solver.Value(work[e, d, s]) == 1:
                    literals.append(work[e, d, s].Not())
                else:
                    literals.append(work[e, d, s])
    model.AddBoolOr(literals)  # "이 해와 완전히 같지는 않아야 한다"
```

### 복수 해 탐색 흐름

```
1차 풀기 → OPTIMAL 확인 → 목적함수 값 저장
    ↓
No-Good Cut 추가 → 2차 풀기
    ↓
목적함수 값 동일? → has_multiple_optimal = True, alt_schedules에 추가
    ↓
최대 (max_alt_solutions - 1)회 반복
```

## 4. 문제 3 — 타이(동등 최적해) 감소 전략

### 타이가 생기는 근본 원인

`target_staff = [2, 2]`처럼 오픈·마감을 동등하게 설정하면 **대칭성**이 발생한다. 예: 화요일에 배정 가능한 직원이 3명인데, 누가 오픈/마감을 맡아도 UNDERSTAFF 패널티가 동일 → 솔버 입장에서 완전히 동등한 해.

이 타이는 구조적 원인이므로 완전히 없애기보다 **최대한 줄이는 전략**을 사용했다.

### 4-1. 휴무 요청 (off_requests) — 2차 수정에서 추가

```python
# employee에 추가 (선택)
"off_requests": [
    {"day": 4, "type": "must"},    # 필수 휴무 — 거의 하드처럼 작동
    {"day": 6, "type": "prefer"},  # 희망 휴무 — 가능하면 배정 안 함
]
```

직원마다 고유한 휴무 요청이 있으면 해 공간이 비대칭해져 많은 타이가 자연히 사라진다. 위반 시 `off_request_violations` 필드에 기록된다.

| 타입 | 패널티 | 동작 |
|------|--------|------|
| `must` | 10,000,000 / 건 | 사실상 하드 제약. 인원 부족이 아니면 100% 준수. |
| `prefer` | 200,000 / 건 | 최대한 준수하되 불가피하면 위반 후 보고. |

### 4-2. 근무일수 균등 배분 (FAIRNESS_W) — 2차 수정에서 추가

직원 간 근무일수 최대-최소 편차를 최소화해 롤링 배분을 유도한다.

```python
FAIRNESS_W = 10  # 타이브레이킹용 미세 조정 (주 목적함수에 영향 없음)

model.AddMaxEquality(max_wd, work_days_vars)
model.AddMinEquality(min_wd, work_days_vars)
# 패널티 += FAIRNESS_W * (max_wd - min_wd)
```

**효과**: W08 완전 스케쥴제 시나리오에서 8명 전원이 고정 휴무 없이도 서로 다른 날 쉬는 롤링 스케줄이 자동 생성됨.

### 4-3. 공휴일 근무 균등 배분 (HOLIDAY_W) — 2차 수정에서 추가

```python
"holiday_indices": [5]    # config에 추가 (선택) — 0-based 날짜 인덱스

HOLIDAY_W = 5  # FAIRNESS_W보다 낮은 가중치
```

공휴일 근무 횟수의 직원 간 편차를 최소화한다.

### 4-4. 역할 제약 (role_level) — 설계 확정, 구현 예정

**설계 변경 이력:**

초기 설계: 숫자가 높을수록 고직급 (점장=4, 사원=1)

```python
# 초기 설계 — 폐기
"shift_requirements": [{"shift": 0, "min_level": 3, "count": 1}]
# 문제: "레벨 3 이상"은 한국어 직관과 반대 방향 (낮은 수가 높은 직급으로 읽힘)
```

**변경 이유:**
1. 한국어 맥락에서 "1등 > 2등"처럼 낮은 숫자가 높은 직급을 의미하는 것이 자연스러움
2. 제약 방향이 `max_level <= X` 형태여야 "레벨 2 이하인 직원"이라는 문장과 일치
3. 매장마다 직급 이름이 다르고(점장/팀장/원장 등) 단계 수도 다양하므로, 이름이 아닌 숫자만으로 처리해야 범용성이 생김
4. 관리자(role_level=1)가 스케줄에 참여하지 않는 경우도 있으므로 `available_days=[]`로 처리, 별도 필드 불필요

**최종 확정 설계:**

```python
# employee에 추가 (선택)
"role_level": 1   # 1=최상위(점장/매니져), 숫자 클수록 낮은 직급
                  # 스케줄 미참여 관리자: available_days=[] 로 표현

# config에 추가 (선택)
"shift_requirements": [
    {"shift": 0, "max_level": 2, "count": 1}
    # → 오픈(shift 0)에 role_level ≤ 2인 직원이 최소 1명
]
```

| 매장 유형 | 직급 구성 예시 |
|----------|-------------|
| 편의점 | 점장(1) → 대리(2) → 주임(3) → 사원(4) |
| 카페 | 매니져(1) → 바리스타(2) → 파트(3) |
| 미용실 | 원장(1) → 디자이너(2) → 인턴(3) |

## 5. 패널티 가중치 계층 설계

```
목적함수 = 인건비 + 야간수당
         + MIN_STAFF_W   × 최소인원_부족_건수       ← 최우선
         + MUST_OFF_W    × 필수휴무_위반_건수        ← 2차 수정 추가
         + SKILL_W       × 필요역량_인원_미달_건수   ← 4차 수정 추가
         + UNDERSTAFF_W  × 목표인원_미달_건수
         + LOW_HOURS_W   × 주15h미만_직원수
         + PREFER_OFF_W  × 희망휴무_위반_건수        ← 2차 수정 추가
         + PREF_W        × 비선호교대_배정_건수
         + FAIRNESS_W    × 근무일수_최대최소_편차    ← 2차 수정 추가 (타이브레이킹)
         + HOLIDAY_W     × 공휴일근무_최대최소_편차  ← 2차 수정 추가 (타이브레이킹)
         + CHANGE_W      × 기존근무표_변경_칸수      ← 3차 수정 추가 (prev_assignments가 있을 때만)
```

| 상수 | 값 | 의미 |
|------|-----|------|
| `MIN_STAFF_W` | 50,000,000 | 최소 인원 1명 부족 |
| `MUST_OFF_W` | 10,000,000 | 필수 휴무 1건 위반 |
| `SKILL_W` | 8,000,000 | 필요 역량 인원 1명 미달 (4차 추가) |
| `UNDERSTAFF_W` | 5,000,000 | 목표 인원 1명 미달 |
| `LOW_HOURS_W` | 2,000,000 | 주 15시간 미만 직원 1명 |
| `PREFER_OFF_W` | 200,000 | 희망 휴무 1건 위반 |
| `PREF_W` | 100,000 | 비선호 교대 배정 1건 |
| `FAIRNESS_W` | 10 | 근무일수 편차 (타이브레이킹) |
| `HOLIDAY_W` | 5 | 공휴일 편차 (타이브레이킹) |
| `CHANGE_W` | 300,000 (`change_weight`로 변경 가능) | 기존 근무표 대비 변경 1칸 |

**설계 원칙**: 상위 항목 1건 위반이 하위 항목 수백 건 위반보다 비싸도록 설정해 우선순위가 확실히 분리된다.

## 6-1. 3차 수정 — 백엔드 연동을 위한 입력 추가

두 필드 모두 **선택**이며, 보내지 않으면 2차 수정본과 동일하게 동작한다. (15개 목 시나리오 결과 동일 확인)

### 재스케줄 시 변경 최소화 — `prev_assignments`, `change_weight`

결원·가용 시간 변경 등으로 같은 기간을 다시 생성할 때, 기존 근무표를 넘기면 바뀌는 칸 수를 최소화한다.

```python
"prev_assignments": {("emp_001", 0): 1, ("emp_002", 0): 0},  # (직원 id, day) → shift
"change_weight": 300_000                                      # (선택) 변경 1칸당 패널티
```

> 백엔드는 JSON으로 튜플 키를 보낼 수 없어 `[{"employee_id", "day", "shift"}]` 배열로 보내고, 연결 스크립트(`run_engine.py`)에서 위 형식으로 변환한다.

### 요일별 교대 근무 불가 — `unavailable_slots`

`available_days`는 요일 단위라, 월요일 09~13시만 가능한 직원도 월요일 저녁 교대에 배정될 수 있었다.
백엔드가 직원의 요일별 가용 시간과 교대 시간을 비교해 근무할 수 없는 (요일, 교대)를 넘긴다.

```python
# employee에 추가 (선택)
"unavailable_slots": [
    {"day": 0, "shift": 2},   # 월요일 저녁 교대 불가
]
```

## 6-2. 4차 수정 — 교대별 필요 역량 인원 (`skill_requirements`)

외국인 손님이 많은 시간대에 일본어 가능자, 음료 제조가 몰리는 시간대에 바리스타처럼
**특정 역량을 가진 직원이 교대마다 일정 인원 이상** 있어야 하는 경우를 처리한다.

```python
# employee에 추가 (선택)
"skills": ["일본어"]

# config에 추가 (선택)
"skill_requirements": [
    {"shift": 0, "skill": "일본어", "count": 1}   # 오전 교대에 일본어 가능자 최소 1명 (매일)
]
```

### 하드가 아닌 고패널티 소프트 제약으로 둔 이유

역량 보유자가 쉬는 날이 하루라도 있으면 하드 제약은 스케줄 전체를 INFEASIBLE로 만든다.
1차 수정에서 최소 인원을 소프트로 바꾼 것과 같은 이유로, 위반 시 큰 패널티를 주고 불가능한 날만 `skill_shortage_report`로 보고한다.

| 비교 대상 | 우선순위 | 이유 |
|-----------|----------|------|
| 최소 인원 (`MIN_STAFF_W` 5천만) | 역량보다 높음 | 사람이 아예 없는 것보다는 역량 없는 사람이라도 있는 게 낫다 |
| 필수 휴무 (`MUST_OFF_W` 1천만) | 역량보다 높음 | 역량 보유자의 필수 휴무를 깨면서까지 채우지 않는다 |
| 목표 인원 (`UNDERSTAFF_W` 5백만) | 역량보다 낮음 | 인원 수를 맞추는 것보다 필요한 역량을 갖추는 게 우선 |

```python
"skill_shortage_report": [
    {"day": 3, "shift": 0, "skill": "일본어", "required": 1, "actual": 0}
]
```

> 4-4절 `role_level`(직급 기반 배치)과는 별개 기능이다. 역할은 숫자 등급 비교, 역량은 보유 여부(태그) 비교라 함께 써도 충돌하지 않는다.

## 6-3. 5차 수정 — 가중치 덮어쓰기(`weight_overrides`), 직원별 시급(`hourly`), 교대별 최대 인원(`max_staff`)

기존 복수 최적해(`alt_schedules`)는 **목적함수 값이 같은 해**만 찾기 때문에, 후보안끼리 성격이 거의 같다.
관리자가 "인건비를 줄인 안"과 "근무일을 고르게 나눈 안"을 비교할 수 있도록, 같은 입력을 **가중치만 바꿔 다시 풀 수 있게** 했다.

```python
# config에 추가 (선택) — 없는 키는 기본값 그대로
"weight_overrides": {
    "FAIRNESS_W": 1_000_000,   # 공평성 우선: 근무일수 편차를 희망 휴무보다 중요하게
}

# employee에 추가 (선택) — 없으면 base_hourly
"hourly": 10030

# config에 추가 (선택, 하드 제약) — 없으면 상한 없음
"max_staff": [2, 3, 2]     # 교대별 최대 인원
```

| 키 | 기본값 | 비고 |
|----|--------|------|
| `MIN_STAFF_W` | 50,000,000 | |
| `MUST_OFF_W` | 10,000,000 | |
| `SKILL_W` | 8,000,000 | |
| `UNDERSTAFF_W` | 5,000,000 | |
| `LOW_HOURS_W` | 2,000,000 | |
| `CHANGE_W` | 300,000 | `change_weight`가 있으면 그 값이 기본값 |
| `PREFER_OFF_W` | 200,000 | |
| `PREF_W` | 100,000 | |
| `FAIRNESS_W` | 10 | |
| `HOLIDAY_W` | 5 | |

- 기존에는 인건비를 모든 직원 같은 `base_hourly`로 계산해서, 시급이 다른 직원 중 누구를 배정해도 비용이 같았다. `hourly`를 넣으면 목적함수와 반환 `cost` 모두 직원별 시급으로 계산하므로 "인건비 우선"안이 실제로 시급이 낮은 직원을 고른다.
- `max_staff`가 없으면 근무일 편차(`FAIRNESS_W`)를 크게 줬을 때 편차를 줄이려고 **필요 없는 인원을 추가 배정**하는 해가 나온다(예: 매일 1명 필요한 교대에 이틀 근무자를 끼워 넣어 4일·4일로 맞춤). 인원 상한을 하드 제약으로 두어 이런 해를 막는다.
- `off_requests`의 각 요청에 `weight`를 주면 그 요청만 다른 패널티를 쓴다. 예를 들어 정규직 필수 휴무를 9백만, 알바 필수 휴무를 기본 1천만으로 두면, 최소 인원(5천만)을 채우려고 누군가의 휴무를 깨야 할 때 정규직 휴무를 먼저 깬다.
- 새 필드를 넣지 않으면 기존과 동일하게 동작한다. 15개 목 시나리오의 상태·인건비·인원 부족 현황이 수정 전과 같음을 확인했다(동점 해 사이의 배정 위치는 수정 전에도 실행마다 달라진다).

## 6-4. 6차 수정 — 월간 희망 제출 연동

앱에서 직원이 **한 달 치 날짜×교대 희망**(가능/선호)과 개인 근무 규칙, 우선순위를 제출하게 되면서 엔진 입력을 넓혔다.
모두 선택 필드라 넣지 않으면 기존과 동일하게 동작한다.

```python
# config에 추가 (선택)
"weeks": [[0], [1,2,3,4,5,6,7], ...],   # 달력 주 단위 묶음. 있으면 주 최대 시간·주 15시간을 주마다 적용
"min_staff_by_day":    [[1,1,1], ...],  # 날짜×교대 최소 인원 (min_staff 대신)
"target_staff_by_day": [[2,3,2], ...],  # 날짜×교대 목표 인원 (target_staff 대신)
"max_staff_by_day":    [[2,3,2], ...],  # 날짜×교대 최대 인원 (하드)
"weekend_days": [0, 6, 7, ...],         # 주말 날짜 인덱스
"open_shifts": [0], "close_shifts": [2],# 마감 다음 날 오픈 판단용
"max_shifts_per_day": 2,                # 쪼개기 근무 허용 (기본 1)
"conflicting_shifts": [[0, 1]],         # 시간이 겹쳐 같은 날 함께 할 수 없는 교대 쌍

# employee에 추가 (선택, 모두 소프트 제약)
"preferred_slots": [{"day": 3, "shift": 0}],  # 날짜×교대 선호 (preferred_shifts 대신). 비어 있으면 선호 없음
"max_weekend_shifts": 2,
"max_consecutive_days": 3,
"no_open_after_close": True,
"min_total_hours": 64, "max_total_hours": 86, # 있으면 이 범위가 '주 15시간 미만' 규칙을 대신한다
"weight_scale": {"PREF_W": 2.0, "RHYTHM_W": 1.6},  # 직원이 정한 우선순위를 배율로

# off_requests 항목에 추가 (선택)
{"day": 5, "type": "prefer", "shifts": [1, 2]}   # 그날 일부 교대만 쉬기 (예: 오후만 쉬기)
```

| 키 | 기본값 | 의미 |
|----|--------|------|
| `WEEKEND_W` | 300,000 | 주말 최대 횟수 1회 초과 |
| `CONSEC_W` | 300,000 | 최대 연속 근무일 초과 구간 1개 |
| `RHYTHM_W` | 300,000 | 마감 다음 날 오픈 1회 |
| `HOURS_W` | 20,000 | 근무량 범위를 벗어난 1시간 |

- 개인 규칙은 직원 본인의 희망이라 **희망 휴무(200,000)와 비슷한 단계**에 두었다. 최소 인원·필수 휴무·역량·목표 인원을 채우려고 필요하면 깨진다.
- 월간(30일)에서 기존 [하드 3]은 주 52시간을 **30일 전체 합계**에 적용해 사실상 월 52시간 상한이 되는 문제가 있었다. `weeks`가 있으면 주마다 적용한다. [소프트 2] 주 15시간 규칙도 7일이 다 들어 있는 주마다 따진다.
- [하드 2]를 2교대까지 풀면 기존 근무일수 변수(`wd`, 상한 D)가 교대 수를 1일 1개로 묶어 버려서, 상한을 `D × max_shifts_per_day`로 늘렸다.
- 8-3(요일별 차등 인원)은 `*_staff_by_day`로 구현했다. 요일별뿐 아니라 특정 날짜(예외일)도 표현한다.

**검증**
- 15개 목 시나리오를 수정 전·후 엔진으로 각각 실행해 상태·인건비·인원 부족 현황을 비교했다. M04만 부족 칸 위치가 달랐는데 총 부족 인원·인건비가 같고, 수정 전 엔진끼리 두 번 실행해도 위치가 달라지는 동점 해 차이다.
- 새 필드마다 작은 입력으로 의도대로 동작하는지 확인했다: 날짜×교대 선호, 토요일 오픈 2명, 14일 기간 주별 시간 상한, 주말 1회 한도, 연속 2일 한도, 마감 후 오픈 금지, 근무량 상한, 오후만 쉬기, 쪼개기 근무와 겹치는 교대 금지, 우선순위 배율.

## 6-5. 7차 수정 — 시간대별 역량과 수습 동행

매장 화면에서 "피크 12–14시 응대 상 1명 필수", "화·금 10–12시 발주 가능자 1명"처럼 **교대와 경계가 다른 시간대**와 **요일**로 역량을 정하고, 수습 직원은 선임과 같이 배치하도록 했다. 모두 선택 입력이다.

```python
# skill_requirements 항목에 추가 (선택)
{"shifts": [0, 1], "skill": "skill_3@HIGH", "count": 1,  # 이 교대들 중 어디에든 있으면 충족 (shift 대신)
 "days": [1, 4],                                      # 이 날짜에만 적용 (없으면 전체)
 "weight": 300_000}                                   # 요구별 패널티 (없으면 SKILL_W). "우선" 역량은 낮게

# employee에 추가 (선택)
"mentor_required_days": [0, 1, 2],  # (하드) 이 날 근무하면 같은 교대에 그날 수습이 아닌 직원이 1명 이상
"max_weekly_hours": 48,             # (하드) 직원별 주 최대 시간. 다른 직장 시간을 뺀 값 (없으면 max_hours)
"avoid_shifts": [2],                # 피하고 싶은 교대. 배정 1건당 AVOID_W(300,000)
"rest_days_together": True          # 7일이 다 있는 주마다 이어진 이틀 휴무가 없으면 REST_PAIR_W(200,000)
```

```python
# config에 추가 (선택, 하드 제약)
"consecutive_days_limit": 5   # 매장 연속 근무 한도. 없으면 기존처럼 4 ([하드 4] 연속 5일 이상 금지)
```

- 역량 등급(상·중·하)은 엔진을 바꾸지 않고 백엔드가 `"skill_3@MID"`처럼 등급별 키를 직원 `skills`에 함께 넣어 처리한다. "중 이상"은 `@MID` 키 보유로 판단한다.
- `skill_shortage_report` 항목에 `"shifts"`가 추가된다. 기존 `"shift"`는 첫 교대로 그대로 둔다.
- 수습 동행은 하드 제약이라 선임이 없는 날에는 수습 직원이 배정되지 않고, 대신 인원 부족으로 보고된다.

**검증**
- 15개 목 시나리오 수정 전·후 비교: M04의 동점 해 배치 차이 외에는 동일 (6차와 같은 결과)
- 작은 예제로 확인: 여러 교대 중 한 곳에 역량자 배치, 지정한 날짜에만 적용, 낮은 가중치의 "우선" 역량은 선호 교대보다 약함, 수습 직원은 선임과 같은 교대, 직원별 주 10시간 상한, 피하고 싶은 교대 미배정, 쉬는 날 이틀 연속, 연속 근무 한도 기본 4일·5일·2일 설정
- 6차 확인 예제 11개도 다시 통과

## 7. 최종 API 명세 (반환 구조)

```python
{
    "status":    "OPTIMAL" | "FEASIBLE" | "INFEASIBLE",
    "schedule":  [{"employee_id": "emp_001", "assignments": [{"day": 0, "shift": 1}, ...]}],
    "cost":      966280,        # 총 인건비 (원), INFEASIBLE이면 None
    "solve_ms":  312,           # 풀이 소요 시간 (밀리초)

    "shortage_report": [        # 최소 인원 미달 (없으면 빈 리스트)
```
